# CLAUDE.md — Photo Library

## Project Overview

Building a searchable, password-protected photo library for a climate charity. Photos live on a shared Google Drive — the library provides a browsable, searchable interface with AI-generated keyword tags and campaign associations inferred from folder structure. Google Drive remains the source of truth for images; the library stores only thumbnails and metadata.

## Architecture

- **Static site**: HTML/JS single-page app hosted on Netlify (free tier)
- **Data**: `data.json` stored in Cloudflare R2 (not in Git — updated by sync functions)
- **Image originals**: Stay on Google Drive (no migration needed)
- **Thumbnails**: Generated during sync, stored in Cloudflare R2 (free tier, minimal storage — ~50MB for ~1000 photos)
- **Sync backend**: GitHub Actions (triggered by Netlify Function or daily cron) — runs Python sync script that scans Drive for new/removed files, generates thumbnails, triggers AI analysis for new photos
- **Image analysis (initial bulk)**: Claude API (Haiku 4.5) — ~$3 for ~1000 images
- **Image analysis (ongoing new photos)**: Claude API (Haiku 4.5) — triggered during sync, only for photos not yet analysed
- **Password protection**: Client-side JS gate (a simple login page that checks a hardcoded password before revealing content — not real security, just a deterrent for casual access). Server-side validation on all Netlify Functions.

## Data Model

Each photo record in `data.json` represents a unique image (by content, not by file). There are two types of grouping:

- **Locations**: Exact duplicates (identical MD5) of the same image in different Drive folders. These are the same file — just stored in multiple places.
- **Alternatives**: Near-duplicate photos (similar perceptual hash) — e.g. burst shots taken seconds apart, slightly different crops. These are different images that share metadata, with one chosen as the primary.

```json
  "added_by": ""

```

**Locations array**: Sorted best-first (highest resolution, largest file size). The `drive_file_url` and `drive_folder_url` at the top level always point to the best copy. When displaying a photo, the UI shows all locations so users can find it in the folder they need.

**Alternatives array**: Similar photos grouped under the primary. The UI shows the primary photo in search results; clicking it reveals an expandable "alternatives" section with thumbnails of the other shots. All alternatives share the same metadata (keywords, description, campaign, etc.). Alternatives also have their own thumbnails in R2.

**Deduplication**: Files with identical MD5 checksums are merged into a single record with multiple `locations`. Near-duplicates (burst shots, crops, resizes) detected by perceptual hashing are grouped as `alternatives` under the highest-resolution primary. This means a burst of 5 similar shots appears once in search results, with the others accessible via "show alternatives".

All metadata fields (`keywords`, `description`, `alt_text`) are editable in the web UI. Initial values are generated by Claude API (Haiku 4.5) during the analysis phase; users can overwrite them at any time. There are no separate AI-specific fields — the AI-generated content is written directly into the main fields.

## Workflow

### Initial Setup (one-time)

1. **Scan Drive**: Python script scans the Shared Drive, catalogues all images, runs dedup, produces a review report
2. **Review report**: Duncan reviews the HTML report (~20-30 min), adjusts dedup decisions
3. **Generate thumbnails**: Download images, create 400px-wide JPEG thumbnails
4. **AI analysis**: Send each image to Claude API for keyword/description generation
5. **Upload to R2**: Upload thumbnails + `data.json` + `campaigns.json` to R2
6. **Deploy site**: Push to GitHub, Netlify auto-deploys

### Ongoing Operation

- **Users upload photos to Google Drive** as they already do — no new workflow to learn
- **Scheduled sync** (GitHub Actions, daily at 6am UTC) runs Python sync script:
  - New files → generate thumbnail, run AI analysis, add to `data.json`
  - Removed files → remove from `data.json`, delete thumbnail from R2
  - Dedup check on new files (MD5 match against existing records)
- **Manual sync button** in the web UI triggers the same sync via Netlify Function → GitHub Actions
- **Metadata editing** happens in the web UI — anyone with the password can edit keywords, descriptions, campaigns, and credits for any photo

## Phases

### Phase 1: Scan and Dedup (DONE)

- Scan Google Drive via API, catalogue all image files
- Three-pass deduplication: exact MD5, perceptual hash, filename patterns
- Logo/design material filtering
- Produce HTML review report
- Scripts: `scan_drive.py`, `dedup_and_filter.py`

### Phase 2: Generate Thumbnails and Analyse (DONE)

- Download approved images from Drive (full resolution needed for thumbnail generation)
- Generate 400px-wide JPEG thumbnails using Pillow (with HEIC support via `pillow-heif`)
- Send each thumbnail to Claude API (Haiku 4.5) for keyword/description generation
- Build initial `data.json` with merged dedup records
- 1831 photos processed, all with keywords and descriptions
- Scripts: `download_and_process.py`, `analyse_photos.py`

### Phase 3: Upload to R2 (DONE)

- Upload thumbnails to R2 (`thumbnails/` prefix)
- Upload `data.json` and `campaigns.json` to R2 bucket root
- Configure CORS headers on R2 bucket
- Script: `upload_to_r2.py`

### Phase 4: Build the Web Interface (DONE)

Single-page app with integrated browsing and metadata editing:

- **Password gate**: simple password input on first visit; stored in sessionStorage
- **Search**: single text input with relevancy-ranked results, searching keywords, description, campaign, credit, alt text, folder path, and filename
- **Browse**: thumbnail grid, click to expand
- **Photo detail view**: shows thumbnail, all metadata, links to Drive (both file and containing folder), and lists all locations where the photo appears
- **Metadata editor** (inline, behind password): edit keywords, description, alt text, campaign, credit for any photo. Save updates `data.json` in R2 via Netlify Function
- **Sync button**: triggers a Drive re-scan via Netlify Function
- **Mobile-friendly** responsive layout
- **Brand**: Possible brand colours (#321D49 purple, #BF0978 magenta), Poppins font, no rounded corners

### Phase 5: Sync Function (DONE)

Python sync script (`scripts/sync.py`) runs in GitHub Actions:
1. Scans Drive for all image files (same logic as `scan_drive.py`)
2. Fetches current `data.json` from R2 and compares
3. For new files: downloads, generates thumbnail, uploads to R2, runs AI analysis, adds record
4. For removed files: removes record from `data.json`, deletes thumbnail from R2
5. For moved files: updates location info
6. Writes updated `data.json` back to R2

Triggered by:
- Daily cron (6am UTC) via GitHub Actions
- Manual "Sync now" button in the web UI (Netlify Function triggers GitHub Actions via `workflow_dispatch`)

The Netlify Function (`sync-drive.js`) is a thin trigger — it calls the GitHub Actions API to start the workflow, avoiding the 10-second Netlify timeout. The Python script runs with no timeout constraints in GitHub Actions.

## Tech Stack

- **Migration scripts**: Python (google-api-python-client, anthropic SDK, Pillow, imagehash, boto3)
- **Sync**: Python script via GitHub Actions (daily cron + manual trigger)
- **Static site**: Vanilla HTML/CSS/JS (no build step)
- **Backend functions**: Netlify Functions (JavaScript/Node.js) — metadata editing + sync trigger
- **Thumbnails + data**: Cloudflare R2 via S3-compatible API
- **Image originals**: Google Drive (unchanged)
- **Image analysis**: Claude API, Haiku 4.5
- **Deployment**: Netlify auto-deploy from GitHub

## Key Constraints

- Running cost must be strictly zero after initial setup (the one-time Claude API cost of ~$3 for bulk analysis is acceptable; ongoing AI analysis for new uploads uses the same API at negligible cost)
- Prefer established, long-lived services (Cloudflare, Netlify, Google)
- Non-technical users interact only with Google Drive (for uploads) and the web UI (for search/metadata editing)
- Password protection is a soft gate (client-side JS + server-side validation on functions), not enterprise-grade auth
- Duncan is the sole technical maintainer — keep the stack simple

## Potential Roadblocks and Difficulties

### 1. Google Drive API for Shared Drives
The Drive API requires `supportsAllDrives=True`, `includeItemsFromAllDrives=True`, and the `driveId` parameter on all calls, or it silently returns zero results. The service account must be added as a member of the Shared Drive. Rate limits are generous (20,000 queries/day) but the script includes backoff logic.

### 2. Netlify Function timeout for sync (SOLVED)
The 10-second Netlify timeout was too tight for a full Drive scan. Solved by moving the sync to a Python script running in GitHub Actions (no timeout constraints). The Netlify Function now just triggers the GitHub Actions workflow via `workflow_dispatch`. For bulk initial processing, use the local Python scripts.

### 3. Google Drive thumbnail links require auth
Drive API thumbnail links (`thumbnailLink`) require authentication — they can't be used directly in a public web page. This is why we generate and host our own thumbnails in R2.

### 4. Distinguishing photos from logos/designed material
The filtering heuristics (dimensions, folder names, file type) catch most cases, but manual review of flagged files is essential. Err on the side of inclusion.

### 5. R2 CORS configuration
The Netlify site needs to fetch `data.json` and thumbnails from R2. CORS rules must be configured explicitly on the R2 bucket.

### 6. Client-side password is not secure
Anyone who views the page source can find the password. Acceptable for a low-sensitivity internal archive. Cloudflare Access (free for up to 50 users) can be added later if needed.

### 7. Concurrent metadata edits
If two people edit metadata at the same time, one edit could be lost. Use R2's `onlyIf` conditional headers (ETag-based optimistic locking) with automatic read-merge-retry (up to 3 attempts).

### 8. Drive folder structure may be chaotic
Campaign inference from folder paths depends on folders being named sensibly. The migration produces a report of inferred campaigns for manual review.

### 9. Perceptual hash threshold tuning
The phash distance threshold (default ~8) may need tuning. The dedup report shows all flagged pairs for manual review.

## Notes

- `data.json` lives in R2, not Git, because it's updated by sync functions and metadata edits.
- At ~500 bytes per record and ~1000 photos, `data.json` will be ~500KB — small enough to fetch on every page load.
- Slug generation handles collisions by appending a numeric suffix.
- EXIF GPS coordinates should be stored internally but NEVER displayed publicly.
- The password is shared via internal channels (email, Slack), not in documentation.
- No folders are excluded from scanning — all Drive folders are included. Dedup handles photos that appear in multiple locations by merging them into a single record with multiple locations listed.
